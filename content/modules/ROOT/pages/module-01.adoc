*Step 1 — About This Lab*

== Objective

By the end of this guided lab exercise, you will be able to:

* Explain the quantum threat to cryptography and "harvest now, decrypt later."
* Identify the post-quantum algorithms standardized by NIST (ML-KEM, ML-DSA, SLH-DSA).
* Confirm that post-quantum cryptography is already available for TLS on Red Hat Enterprise Linux 10.
* Deploy a web application as an *nginx systemd service* and serve it over HTTPS.
* Watch a post-quantum requirement *break* the connection to that web server, then diagnose and fix it.
* Harden the web server so that it *requires* post-quantum TLS key exchange.

== Introduction

Learn how to protect web traffic (HTTPS/TLS) against future quantum computers using Red Hat
Enterprise Linux 10 — by breaking a web app on purpose and then fixing it.

Almost every secure connection you use today — HTTPS, VPNs, and SSH — relies on public-key
cryptography such as RSA and elliptic curve. A sufficiently powerful *quantum computer* could
break those algorithms. The threat is not only in the future: in a *"harvest now, decrypt
later"* attack, an adversary records your encrypted traffic today and simply waits for a
quantum computer to decrypt it later. Any secret that must stay confidential for years is
already at risk.

To address this, in 2024 NIST standardized a new family of *post-quantum* algorithms built on
math problems that neither classical nor quantum computers are known to solve efficiently:
*ML-KEM* (FIPS 203, key exchange), *ML-DSA* (FIPS 204, signatures), and *SLH-DSA* (FIPS 205,
signatures).

Red Hat Enterprise Linux 10 is built to be *post-quantum capable*: these algorithms ship in its
core cryptographic libraries, including *OpenSSL 3.5*, which powers TLS for web servers like
nginx and Apache. In this lab you will use that capability to make HTTPS — the protocol behind
every web application — resistant to the quantum threat.

[NOTE]
====
This lab runs on *RHEL 10.1 or later*, where the post-quantum TLS key-exchange group is part of
the `DEFAULT` system-wide crypto-policy. That means the building blocks for PQC are *already on*
— there are no preview packages to install. But as you will see, a web server that was
configured without PQC in mind will still *break* the moment a client insists on post-quantum
security. You will deploy such a server, watch it break, and fix it.
====

=== Lab Modules

. *About This Lab* — You are here: the quantum threat, PQC for TLS, and the lab environment.
. *Your Post-Quantum Foundation* — Confirm PQC for TLS is available in OpenSSL and the crypto-policy.
. *Deploy the Web App as a Service* — Run Super-Business's web server as an nginx systemd service over HTTPS.
. *Turn On PQC — Watch It Break* — Require post-quantum TLS from the client and watch the app fail.
. *Diagnose and Fix* — Read the logs, fix the server's TLS configuration, and restore service with PQC.
. *Require Post-Quantum TLS* — Harden the server so it *only* accepts post-quantum key exchange.
