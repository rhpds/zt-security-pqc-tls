= Your Post-Quantum Foundation

Before deploying anything, let's confirm that post-quantum cryptography for TLS is already
available on this RHEL 10 system. On RHEL 10.1 and later you do *not* install anything or flip a
preview switch — the building blocks are part of the standard configuration.

== Step 1 — Confirm the operating system

[source,bash,role=execute]
----
cat /etc/redhat-release
----

== Step 2 — Check the OpenSSL version

TLS on RHEL is powered by *OpenSSL*. Post-quantum key exchange for TLS arrived in OpenSSL 3.5,
which ships in RHEL 10. Confirm it:

[source,bash,role=execute]
----
openssl version
----

You should see `OpenSSL 3.5` (or later).

== Step 3 — Look at the system-wide crypto policy

RHEL controls which cryptographic algorithms every compliant application may use through a
single system-wide setting called the *crypto-policy*. Show it:

[source,bash,role=execute]
----
update-crypto-policies --show
----

You should see `DEFAULT`. On RHEL 10.1+, the `DEFAULT` policy *already includes* the post-quantum
TLS key-exchange group — there is nothing extra to enable at the system level.

== Step 4 — See which TLS key-exchange groups OpenSSL supports

In TLS 1.3, the client and server agree on a shared session key using a *key-exchange group*.
Ask OpenSSL which groups it offers, and filter for the post-quantum entry:

[source,bash,role=execute]
----
openssl list -tls-groups | grep -i mlkem
----

You should see entries including:

[source,text]
----
X25519MLKEM768
----

[IMPORTANT]
====
`X25519MLKEM768` is a *hybrid* post-quantum key-exchange group. It combines the classic X25519
elliptic-curve exchange with the post-quantum *ML-KEM-768* (FIPS 203). The shared secret stays
safe unless *both* are broken — so you get post-quantum protection today without giving up the
proven classical algorithm. This is the single most important defense against "harvest now,
decrypt later" for HTTPS.
====

[TIP]
====
Because this is governed by the system-wide crypto-policy, *every* crypto-policy-aware
application on the host — OpenSSL, nginx, Apache httpd, GnuTLS — can pick up post-quantum support
from the same setting. But an application can still *override* the policy with its own
configuration. That is exactly the trap you will walk into in the next few modules.
====

Your foundation is in place: RHEL 10 and OpenSSL 3.5 can do post-quantum TLS. In the next module
you will deploy a real web application as a systemd service and connect to it.
